# Compatibility

The ILP, IL-DCP, STREAM, HTTP-signature and Open Payments client rows were differentially tested against the official
packages (byte for byte, on seeded random input, or against one shared HTTP server), except the `/plain/*` rows, which wrap
the same code and are tested on their own only. The GNAP server rows are checked by
[`test/gnap-server/rafiki-parity.test.ts`](https://github.com/dayjobdoor/open-payments-ilp/blob/main/test/gnap-server/rafiki-parity.test.ts), a hand-ported table of cases from Rafiki's auth tests (Rafiki `58430af8`,
2026-10-09; nothing links it to Rafiki, so a Rafiki change goes unnoticed) and by the official client's flows; the
webhook rows by a reimplementation of Rafiki's signer. **match** = same observable behaviour; **deviation** =
deliberate, with the reason.

## ILP, IL-DCP, STREAM

| Counterpart                                                                                                                                               | Status    | Notes                                                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/ilp` vs [`ilp-packet`](https://www.npmjs.com/package/ilp-packet) codec, addresses, OER                                                                  | match     | Byte-identical both directions; accepts nothing `ilp-packet` rejects except an epoch `expiresAt` (`19700101000000000`).                                                                                                                                            |
| `/plain/ilp`, `/plain/ildcp` vs `ilp-packet`, `ilp-protocol-ildcp` | deviation | Same function names (`serializeIlpPrepare`, ...) and exceptions instead of `Result`, but `Uint8Array` where upstream uses `Buffer`, `bigint` amounts and `Date` expiries; they throw `IlpCodecError`. `fetchIldcp(sendData, { clock, ttlMs })` has its own signature, not a port of upstream's `fetch`. Thin wrappers over `/ilp` and `/ildcp`, so the byte-level rows above apply; the wrappers themselves are not differentially tested. |
| `/ilp` leniency                                                                                                                                           | deviation | Rejects calendar-invalid timestamps, non-ASCII in ASCII fields, non-printable reject codes, data over 32767. Years 0000–0099 stay literal (`ilp-packet` maps to 19xx).                                                                                             |
| `/ildcp` vs [`ilp-protocol-ildcp`](https://www.npmjs.com/package/ilp-protocol-ildcp)                                                                      | match     | Byte-identical; `serveIldcp` answers `F00` for bad, foreign or expired requests, and when `now` is an Invalid Date (the reference reads `Date.now()`).                                                                                                                                                                                   |
| `/ildcp` clock and `fetch(sendData)`                                                                                                                      | deviation | The codecs never read the clock (`expiresAt`, `now` are explicit) and there is no transport of its own. `fetchIldcp(sendData, { clock, ttlMs })` takes the transport as a callback like upstream's `fetch(sendData)`, reads the clock only through `clock` (default `new Date()`; the request is valid for `ttlMs`, 30 s by default), and a connector Reject fails with `IlpCodecError` (`invalid-type`) that names its `code` and `message`.                                                                                      |
| `/ilp` `postPrepare` vs [ILP over HTTP (RFC 35)](https://interledger.org/developers/rfcs/ilp-over-http/) | deviation | Synchronous profile only: no `Request-Id` / `Callback-Url` / `Prefer` and no `202` handling, so any `2xx` is taken as the reply. Redirects are never followed (a `3xx` is `network`), the reply is capped (`maxReplyBytes`, 64 KiB) and the exchange times out (`timeoutMs`, 30 s), and a `token` that is not a valid header value is `invalid-option` instead of a runtime `TypeError`. Not differentially tested: there is no reference client to compare with. |
| `/stream` packets, frames, crypto vs [`ilp-protocol-stream`](https://www.npmjs.com/package/ilp-protocol-stream)                                           | match     | Byte-identical, cross-decryptable; receipts (RFC 39) interoperate both ways.                                                                                                                                                                                       |
| `/stream` receiver, credentials, `decodeStreamPaymentTag` vs [`@interledger/stream-receiver`](https://www.npmjs.com/package/@interledger/stream-receiver) | match     | Same decision order and encoding; an empty `paymentTag` means no tag. Pending replies always carry `dataFrames` (possibly empty).                                                                                                                                  |
| `/stream` token decoding                                                                                                                                  | deviation | Exact base64url alphabet; a malformed segment is `F06`.                                                                                                                                                                                                            |
| `/stream` sender vs `@interledger/pay`                                                                                                                    | deviation | No quote, rate probe loop or `pay` loop (they need a transport, timers, congestion state). Primitives are provided: probes, `minDestinationAmount`, `decryptStreamPacket`, receipts, `planStreamChunks`. `minDestinationAmount` defaults to `amount` (same asset). |
| `/plain/stream` | deviation | Same wire behaviour as `/stream` (thin wrapper). Frame and packet codecs throw `IlpCodecError`, crypto and receiver functions reject with `StreamError`, and the pending reply's `accept` / `temporaryDecline` / `finalDecline` return `Promise`s. Not differentially tested on its own. |

## HTTP signatures and webhooks

| Counterpart                                                                                                                          | Status    | Notes                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/http-signatures` signing vs [`@interledger/http-signature-utils`](https://www.npmjs.com/package/@interledger/http-signature-utils) | match     | Same components, `sha-512` digest, `sig1`; both verify each other's signatures. `Content-Digest` is over the exact bytes sent (compact JSON from this client); Rafiki's verifiers digest `JSON.stringify` of the parsed body, so only compact JSON verifies there. Optional `tag`.                                                           |
| `/http-signatures` verification                                                                                                      | deviation | Stricter: strict RFC 8941, `created` required (300 s age, 30 s skew), a non-empty body must be digest-covered (`requireBodyDigest: false` opts out), `alg`, when present, must be `ed25519` (`forbidAlg: true` refuses it), the body read is capped (`maxBodyBytes`). Looser: no content-length/type demand when the digest is covered; the digest is checked over the exact body bytes. `verifyRequest` checks `sig1` unless `label` names another signature; the GNAP server tries up to three labels (Rafiki reads `sig1` only). |
| `/http-signatures` keys                                                                                                              | match     | `importEd25519PrivateKeyPem` (PKCS#8), `exportPublicJwk(key, { keyId })`. Base64-wrapped PEM (upstream's `loadBase64Key`): decode first.                                                                                                                                                                                                                |
| `/webhooks` vs Rafiki `generateWebhookSignature`                                                                                     | match     | Same HMAC over `<t>.<JCS body>` and header `t=<ms>, v<N>=<hex>` (the version is only a label in Rafiki); default `v1`; tested against a reimplementation of the signer. JCS follows `json-canonicalize` (the library Rafiki signs with), including its `toJSON` and `Date` handling, with no nesting limit; the oracle test generates both. Event types from the OpenAPI document. `version` must be a non-negative safe integer, else `invalid-config` (Rafiki only ever signs `v1`). The window keeps no state: de-duplicate on the event `id`.                                                                                                                       |
| `/plain/http-signatures`, `/plain/webhooks` | deviation | Same behaviour as the Effect entries, with `Promise`s and exceptions. `verifyRequest`'s `resolveKey` is a plain (async) function: `null`/`undefined` is `unknown-key`, a thrown `HttpSignatureError` passes through, and any other throw rejects as it is. Not differentially tested on its own. |
| `/webhooks` verification                                                                                                             | deviation | Requires the header, enforces a replay window (300 s) and future skew (30 s); Rafiki's POS middleware accepts a missing header and ignores the timestamp.                                                                                                                                                                                    |
| `/webhooks` receiving                                                                                                                | n/a       | Rafiki sends `{ id, type, data }` with a 2 s timeout and counts only HTTP `200` as delivered (up to 10 retries): answer `200`.                                                                                                                                                                                                               |

## Open Payments client

| Counterpart ([`@interledger/open-payments`](https://www.npmjs.com/package/@interledger/open-payments) 7.4) | Status    | Notes                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Routes, URLs, verbs, query handling, signing rule, headers                                                 | match     | Every route; both clients run against one verifying server, except `grant.cancel`, `token.revoke`, `incomingPayment.getPublic`, `outgoingPayment.get` / `list` and the unauthenticated client, which only `client.test.ts` exercises (against the fake server).                                                                                                                                                |
| Types, constants, payment invariants, grant-request checks, `OpenPaymentsClientError` fields               | match     | Mutual type assignability asserted; request checks return `invalid-request`, the amount helpers `invalid-amount`, and a response that breaks a payment invariant `validation`, instead of throwing.                                                                                         |
| Response validation                                                                                        | deviation | Effect Schema validation, body returned as received (unknown members kept). Schemas that forbid extra members upstream (quote, outgoing-payment, ilp-payment-method, page-info, JWKS) accept them here; `assetScale` 0-255 and uint64 amounts are enforced as the OpenAPI documents say, and a pending grant needs `interact.finish`. The `ilp` payment method's `ilpAddress` (at most 1023 characters, ILP address pattern) and `sharedSecret` are checked against the OpenAPI patterns. Looser than the OpenAPI documents and the reference client (AJV): `format: uri` / `date-time`, the `receiver` pattern, `access` `maxItems` / `uniqueItems`, integer-ness of `expires_in` and `wait`, page-info cursor `minLength`. `failed` is required here, optional upstream.    |
| Request URLs, redirects, response size | deviation | Deliberate hardening: only `https:` URLs (`http:` with `useHttp`), without credentials or fragment, optionally narrowed by `urlPolicy`, else `invalid-request` before any I/O; redirects are not followed (`transport`); a response over `maxResponseBytes` (1 MiB) is refused (`transport`; for a 4xx or 5xx it is an `http` error with its `status`, retried by status and `Retry-After` like any other). A `urlPolicy` admits a URL only by returning `true` (a throw, a Promise or any other value is `invalid-request`); without one, loopback, private and link-local hosts are requested, and a name that resolves to a private address cannot be caught at this layer. `requestTimeoutMs` is 0-2147483647 and `retry` delays are finite and at least 0, else `invalid-request`. |
| Factory                                                                                                    | deviation | Synchronous, takes a `CryptoKey` (no filesystem/`Buffer`). No pino logger, no `authenticatedRequestInterceptor` (experimental upstream).                                                                   |
| `/plain/open-payments` factory and errors | deviation | `await createAuthenticatedClient(...)` takes a `CryptoKey`, a private JWK or a PEM string (no file path, no `KeyObject`). Failures reject with `OpenPaymentsError`, so `instanceof OpenPaymentsClientError` does not match. The client types are asserted assignable to upstream's `AuthenticatedClient` and `UnauthenticatedClient` (`test/plain/upstream-compat.test.ts`; a type-level check that only `tsc -p tsconfig.test.json` runs). |
| Retry                                                                                                      | deviation | Opt-in `retry` option (backoff + jitter, `Retry-After`, re-signed per attempt; `POST` only with `retryNonIdempotent`, which the client-wide flag does not grant to `token.rotate` and `grant.continue`; a `Retry-After` over `maxDelayMs` ends the retries); off by default, `Effect.retry` still composes (errors expose `status`, `attempts`). |

| Not implemented                                                                       | n/a       | String access references, the `bearer` flag (it would let a resource server skip signature checks; stays `400 invalid_flag`), `user_code` / `app` start, `user` / `display` claims, key proofs other than `httpsig`, subject assertions.                                                                                             |

## GNAP client (`open-payments-ilp/hono`)

RFC 9635 is the standard the middleware follows; where Rafiki / Open Payments servers differ it accepts both.

| RFC 9635 client behaviour                      | Status    | Notes                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Grant request, continuation, token management  | match     | Signed as §7.3.1 (components, `created`, `keyid`, `nonce`, `tag="gnap"`, no `alg`; sha-256 digest for the inline key, sha-512 for a wallet-address `client` like the official client), `Authorization: GNAP`, `wait` (5 s default) never cut short, one-time `interact_ref`.                                                    |
| Denial                                         | match     | `user_denied` / `request_denied` on the continue call (§3.6, §4.2) and Rafiki's `result=grant_rejected` both end in `401`.                                                                                                                                                                                                      |
| Redirects, URLs, error text                    | deviation | Redirects are never followed. The grant endpoint, `continue` and `manage` URIs must be `https:` (`http:` on loopback) and carry no userinfo. An error answer never repeats the server's text or the URLs it named. |
| Relative `redirectUri`                         | deviation | Resolved against `externalUrl`, or against the request only when its host is loopback and no proxy header (`X-Forwarded-*`, `Forwarded`) came with it; on a public host without `externalUrl` the middleware answers `500` instead of trusting `Host`. |
| What starts a login                            | deviation | Only a `GET` navigation (`Sec-Fetch-Mode: navigate`, or no such header and `Accept: text/html`), never a prefetch; every other request without a session gets `401`. |
| Concurrent refresh                             | deviation | Requests with the same expired session merge into one rotation per process; a page load that loses the race to another instance is redirected once to the same URL. |
| `client` as a wallet address URL               | deviation | §2.3: a string is an instance identifier the AS already knows; Open Payments: the wallet address whose `jwks.json` holds the key. `client` must be an http(s) URL (the middleware does not fetch it). Without `client` the key is sent inline.                                                                                                                                                      |
| `access_token.manage` as a URL string          | deviation | §3.2.1: object with a management token that differs from the access token; Rafiki/Open Payments: a URL authorised by the access token itself. Both are accepted.                                                                                                                                                                |
| Finish `hash` encoding and `result=` redirects | deviation | §4.2.1, §4.2.3: unpadded base64url, `hash` and `interact_ref` always; Rafiki/Open Payments: padded base64, and `result=grant_rejected` without `hash` for a denial. Both are accepted.                                                                                                                                          |
| `http:` grant, continue and manage URIs        | deviation | §11.1: TLS; Rafiki's local environments talk plain HTTP between containers. Callback and interaction URIs must be `https:` or `localhost` (§2.5.2.1, §4.1.1).                                                                                                                                                                   |
| Cookies hold the pending grant and the session | match     | §11.26: the cookies are AES-256-GCM encrypted (key derived from `secret` with HKDF), httpOnly, Secure and `SameSite=Lax`, so the browser's owner cannot read them; still storage-less like `oidc-auth`. `encryptCookies: false` stores them signed only (readable).                                                             |
| Polling without `finish`                       | match     | §5.2, §3.1: a grant with `continue` and no `interact.finish` is polled by the browser's next navigations, never before `wait`. Pending: `302` to `interact.redirect` (`202` + `Retry-After` when none is offered); denial `401`; approval continues the request.                                                                |
| `interact.expires_in`                          | match     | §3.3: shortens the ten minutes of the pending state and pointer (whole seconds); 0 or less is `502`.                                                                                                                                                                                                                            |
| Signing-key rotation                           | n/a       | §6.1.1 (rebinding a token's key with two signatures) is not implemented.
